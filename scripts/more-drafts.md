# 자세한 설명 초안

> `용어 이름 | 자세한 설명` 한 줄씩. `npm run build:terms`가 읽어서 terms.json의 `more`에 넣어요. 상세 화면의 [자세히 보기]를 누르면 펼쳐져요.
> 규칙: 기본 설명(쉬운 뜻)보다 한 걸음 더. 쉬운 말 · 3~4문장 · 끝말 "~예요/~해요" · 왜 필요한지, 언제 만나는지, 비유나 예시 하나
> 문장 사이를 ` // `로 나누면 줄을 바꿔서 보여 줘요.
> 모두 Claude가 쓴 초안이에요. 고치고 싶으면 이 파일에서 문장만 바꾸면 돼요.

## 기본 말
바이브코딩 | 코드를 한 줄도 몰라도, 만들고 싶은 것을 말로 설명하면 AI가 코드를 대신 써 줘요. // 나는 "무엇을, 어떻게" 설명하고, 결과를 눌러 보며 "여기를 이렇게 바꿔 줘" 하고 고쳐 나가요. // 요리사에게 주문하는 손님 같아요. 요리법은 몰라도 원하는 맛을 정확히 말하면 돼요. 그래서 이 사전처럼 정확한 이름을 아는 게 중요해요.

미리보기 | 만든 것을 다른 사람에게 보여 주기 전에 나만 먼저 확인하는 화면이에요. // 학습지를 인쇄하기 전에 '인쇄 미리보기'로 한 번 보는 것과 같아요. // 여기서 버튼을 눌러 보고, 이상한 곳을 찾아 AI에게 고쳐 달라고 해요.

웹앱 | 브라우저에서 열리지만, 앱처럼 누르고 입력하고 저장하는 일을 하는 페이지예요. // 퀴즈, 출석 체크, 모둠 뽑기, 타이머처럼 '쓰는' 것이면 웹앱이에요. // 따로 설치하지 않아도 주소만 있으면 휴대폰, 태블릿, 컴퓨터 어디서나 열려서 수업에 쓰기 좋아요.

무료 한도 | 돈을 내지 않고 쓸 수 있는 정해진 양이에요. 하루 대화 수, 저장 용량, 방문자 수 같은 거예요. // 한도를 넘으면 잠시 멈추거나, 다음 날까지 기다리거나, 요금이 생겨요. // 수업 시간에 갑자기 멈추지 않게, 쓰는 도구의 무료 한도를 미리 확인해 두면 좋아요.

## 컴퓨터와 브라우저
브라우저 | 인터넷 페이지를 열어 보여 주는 프로그램이에요. 크롬, 엣지, 사파리, 웨일이 있어요. // 같은 페이지도 브라우저마다 아주 조금씩 다르게 보일 수 있어요. // 만든 웹앱이 이상하면 "크롬에서는 되는데 사파리에서는 안 돼요"처럼 어느 브라우저인지 함께 말해 주면 좋아요.
주소 | 인터넷 페이지마다 하나씩 있는 집 주소예요. 화면 맨 위 주소창에 보여요. // https://로 시작하고, 이 주소를 알려 주면 누구나 같은 페이지에 찾아올 수 있어요. // 학생들에게 나눠 줄 때는 주소를 QR 코드로 바꾸면 편해요.
새 탭 / 새 창 | 지금 보던 페이지는 그대로 두고, 다른 페이지를 하나 더 여는 거예요. // 탭은 한 창 안에 책갈피처럼 나란히 생기고, 창은 아예 따로 떠요. // 링크를 눌렀을 때 학생들이 원래 화면을 잃지 않게 하려면 "새 탭으로 열리게 해 줘"라고 하면 돼요.
시크릿 창 | 방문 기록, 로그인, 저장된 파일 없이 '처음 온 사람'처럼 여는 창이에요. // 고쳤는데 화면이 그대로일 때, 시크릿 창으로 열어 보면 예전 파일(캐시) 때문인지 바로 알 수 있어요. // 학생 입장에서 처음 들어왔을 때 어떻게 보이는지 확인할 때도 좋아요.
쿠키 | 사이트가 내 브라우저에 남겨 두는 작은 메모예요. // "이 사람은 로그인했음", "글자 크기는 크게" 같은 걸 기억해서 다음에 와도 그대로 보여 줘요. // 쿠키를 지우면 로그인이 풀리고 설정이 처음으로 돌아가요.
팝업 차단 | 페이지가 멋대로 새 창을 띄우지 못하게 브라우저가 막는 기능이에요. // 광고 창을 막아 주는 고마운 기능이지만, 내가 만든 앱의 새 창도 막힐 수 있어요. // "아무 반응이 없어요"일 때 주소창 오른쪽에 차단 표시가 있는지 확인해 봐요.
다운로드 / 업로드 | 인터넷에 있는 걸 내 컴퓨터로 받아 오는 게 다운로드, 내 컴퓨터에 있는 걸 인터넷으로 올리는 게 업로드예요. // 학습지 파일을 받는 건 다운로드, 과제 사진을 제출하는 건 업로드예요. // 앱에서 "사진을 올릴 수 있게 해 줘"라고 하면 업로드 기능을 만들어 달라는 뜻이에요.
압축 파일 | 여러 파일을 봉투 하나에 담아 묶은 파일이에요. 이름 끝이 .zip이에요. // 파일이 많을 때 한 번에 주고받기 편하고, 크기도 조금 줄어요. // 열어서 쓰려면 먼저 "압축 풀기"를 해야 해요. 압축 안에서 바로 열면 제대로 안 될 때가 많아요.
확대·축소 | Ctrl을 누른 채 마우스 휠을 돌리면 화면 전체가 커지고 작아져요. Ctrl+0을 누르면 원래대로 돌아와요. // 프로젝터로 보여 줄 때 글자를 키우기 좋아요. // 화면이 이상하게 크거나 작아 보이면, 실수로 확대·축소가 된 건 아닌지 먼저 확인해 봐요.
자주 쓰는 단축키 | 키 두 개를 함께 눌러 빠르게 하는 일이에요. // 복사 Ctrl+C, 붙여 넣기 Ctrl+V, 되돌리기 Ctrl+Z, 전체 선택 Ctrl+A, 저장 Ctrl+S, 강력 새로고침 Ctrl+Shift+R. // 바이브코딩에서는 "전체 선택 → 복사 → 붙여 넣기"를 아주 많이 써서, 이것만 알아도 훨씬 빨라져요.
캡처 | 지금 보이는 화면을 사진처럼 찍는 거예요. 윈도우는 Win+Shift+S, 맥은 Cmd+Shift+4예요. // 화면이 이상할 때 말로 설명하기보다 캡처해서 AI에게 보여 주면 훨씬 정확하게 고쳐 줘요. // "이 부분이 이렇게 보여요"라고 한 줄 덧붙이면 더 좋아요.

## AI 답변 읽기
코드 블록 | AI 답변 속에 회색이나 검은 상자로 따로 묶인 부분이에요. 그 안에 든 게 진짜 코드예요. // 상자 밖의 글은 설명이고, 상자 안의 글만 파일에 넣어요. // 상자 오른쪽 위의 복사 버튼을 누르면 한 글자도 빠짐없이 복사돼요.
통째로 복사 | 코드를 마우스로 드래그해서 고르면 처음이나 끝이 빠지기 쉬워요. // 코드 상자 오른쪽 위 복사 버튼을 누르면 전부 정확하게 복사돼요. // 괄호 하나만 빠져도 전체가 안 움직이니까, 코드는 늘 통째로 복사해서 통째로 바꿔 넣어요.
마크다운 | 글 앞에 # 를 붙이면 제목, **글**은 굵게, - 를 붙이면 목록이 되는 간단한 글쓰기 방법이에요. // AI 답변도 이 방법으로 써서 제목과 목록이 예쁘게 보여요. // README 파일이나 노션에서도 쓰여서, 알아 두면 기획서를 정리할 때도 편해요.
줄 번호 | 코드 왼쪽에 1, 2, 3 하고 붙은 숫자예요. 코드의 일부가 아니라 위치를 알려 주는 표시예요. // 에러 메시지에 "42번째 줄"이라고 나오면 이 번호로 찾아가요. // AI에게 "30번째 줄 버튼 색을 바꿔 줘"처럼 짚어 말하면 더 정확해요.
들여쓰기 | 줄 앞에 넣은 빈칸이에요. 어떤 코드가 어떤 코드 '안에' 들어 있는지 보여 줘요. // 목차에서 하위 항목을 안쪽으로 들여 쓰는 것과 같아요. // 복사하다가 들여쓰기가 흐트러지면 읽기 어려워지고, 어떤 언어(파이썬)에서는 아예 오류가 나요.
괄호 짝 | ( ), { }, [ ]는 여는 것과 닫는 것이 꼭 짝을 이뤄야 해요. // 문장의 따옴표를 열고 안 닫으면 어디까지가 인용인지 모르는 것처럼, 하나만 빠져도 컴퓨터가 어디까지인지 몰라서 전체가 멈춰요. // 코드 일부만 고쳐 넣다가 자주 생기니, 고친 부분을 통째로 바꿔 넣는 게 안전해요.
따옴표 | 코드에서 글자는 곧은 따옴표(" " 또는 ' ') 안에 넣어요. // 한글 문서나 메신저에서 복사하면 둥근 따옴표(“ ”)로 바뀌어 섞이는데, 컴퓨터는 이걸 다른 글자로 봐서 오류가 나요. // 코드는 메모장이나 AI 답변의 복사 버튼으로 옮기는 게 안전해요.
대소문자 구분 | 코드는 영어 대문자와 소문자를 완전히 다른 글자로 봐요. Button과 button은 서로 다른 이름이에요. // 파일 이름도 마찬가지라 Cat.png와 cat.png를 헷갈리면 그림이 안 떠요. // 그래서 파일 이름은 처음부터 모두 소문자로 쓰는 습관이 좋아요.
생략된 코드 | AI가 답을 짧게 하려고 "// 나머지는 그대로"나 "..."처럼 일부를 줄여 쓴 거예요. // 이걸 그대로 붙여 넣으면 줄여 쓴 부분의 코드가 통째로 사라져서 앱이 망가져요. // 이런 표시가 보이면 "생략하지 말고 전체 코드로 다시 줘"라고 요청해요.

## 자주 만나는 문제
흰 화면 | 페이지를 열었는데 아무것도 없이 하얗기만 한 상태예요. // 대부분 코드 어딘가에 오류가 있어서 화면을 그리다 멈춘 거예요. // F12를 눌러 콘솔에 빨간 글자가 있는지 보고, 그 글을 통째로 복사해서 AI에게 주면 빨리 고칠 수 있어요.
에러 | 앱이 멈추거나 기능이 안 되게 만드는 문제예요. 콘솔에 빨간 글자로 떠요. // 신호등의 빨간불처럼 '여기서 멈췄어요'라는 뜻이라 꼭 고쳐야 해요. // 에러 메시지에는 무엇이, 몇 번째 줄에서 잘못됐는지 적혀 있어서, 통째로 복사해 AI에게 주면 돼요.
경고 | 앱은 돌아가지만 '이렇게 하면 더 좋아요'라고 알려 주는 문제예요. 콘솔에 노란 글자로 떠요. // 신호등의 노란불처럼 조심하라는 뜻이고, 당장 멈추지는 않아요. // 급한 에러부터 고치고, 경고는 나중에 한꺼번에 정리해도 괜찮아요.
한글 깨짐 | 한글이 ?, �, 이상한 기호로 바뀌어 보이는 거예요. // 컴퓨터가 글자를 저장하는 방식(인코딩)이 서로 안 맞아서 생겨요. // 파일을 UTF-8로 저장하고, HTML 맨 위에 <meta charset="UTF-8">이 있으면 대부분 해결돼요. AI에게 "한글이 깨져"라고 하면 넣어 줘요.
그림 깨짐 | 그림이 있어야 할 자리에 깨진 아이콘이나 빈칸만 보이는 거예요. // 대부분 파일 이름이나 위치(경로)가 코드에 적힌 것과 조금 달라서 그래요. 대소문자 하나만 달라도 못 찾아요. // 그림 파일 이름과 코드 속 이름을 나란히 놓고 한 글자씩 비교해 봐요.
반영 안 됨 | 분명히 고쳤는데 화면이 예전 그대로인 거예요. // 저장을 안 했거나, 브라우저가 예전 파일(캐시)을 보여 주고 있을 때가 많아요. // 저장 → Ctrl+Shift+R(강력 새로고침) → 시크릿 창으로 열기 순서로 확인하면 거의 해결돼요.
멈춤 | 화면이 굳어서 눌러도 아무 반응이 없는 거예요. // 끝나지 않고 계속 도는 반복 코드나, 너무 무거운 작업이 원인일 때가 많아요. // 탭을 닫고 다시 열어 보고, "버튼을 누르면 화면이 멈춰요"처럼 언제 멈추는지 AI에게 알려 줘요.
고치다 더 망가짐 | 하나를 고쳤더니 잘 되던 다른 곳이 망가지는 거예요. 아주 흔한 일이에요. // 코드는 서로 이어져 있어서, 한 곳을 바꾸면 다른 곳에 영향을 줄 수 있어요. // 잘 될 때마다 버전을 저장해 두면 "아까 그 버전으로 돌려 줘"라고 쉽게 되돌릴 수 있어요.
휴대폰에서만 이상함 | 컴퓨터에서는 멀쩡한데 휴대폰에서 글자가 넘치거나 버튼이 잘리는 거예요. // 휴대폰은 화면이 좁고, 손가락으로 누르고, 브라우저도 조금 달라서 생겨요. // 컴퓨터에서 F12 → 기기 모드로 휴대폰 크기를 미리 확인하고, 캡처해서 AI에게 보여 주면 좋아요.

## 코드 기본
HTML · CSS · 자바스크립트 | 웹페이지는 세 가지 언어가 힘을 합쳐 만들어요. // HTML은 "여기에 제목, 여기에 버튼"처럼 뼈대를 세우고, CSS는 색·크기·모양을 입히고, 자바스크립트는 "누르면 점수가 올라가"처럼 움직임을 맡아요. // 사람으로 치면 뼈대, 옷, 행동이에요. 프롬프트에서 "모양만 바꿔 줘"는 CSS, "기능을 더해 줘"는 자바스크립트를 고쳐 달라는 뜻이에요.
프론트엔드 | 사용자가 눈으로 보고 손으로 누르는 화면 쪽이에요. 버튼, 글자, 그림, 움직임이 모두 여기에 있어요. // 식당으로 치면 손님이 앉는 홀이에요. // 바이브코딩으로 만드는 교실 앱은 대부분 프론트엔드만으로도 충분해요.
백엔드 | 화면 뒤에서 데이터를 저장하고, 로그인을 확인하고, 계산하는 쪽이에요. 사용자 눈에는 안 보여요. // 식당으로 치면 손님은 못 보는 주방이에요. 홀에서 받은 주문을 주방이 처리해서 내보내요. // 여러 사람이 같은 기록을 보거나 로그인이 필요할 때 백엔드가 필요해져요.
컴포넌트 | 버튼, 카드, 메뉴처럼 화면을 이루는 조각을 하나로 묶어 이름 붙인 거예요. // 레고 블록처럼 한 번 만들어 두면 여러 곳에 끼워 쓸 수 있어요. 버튼 하나만 고치면 그 버튼이 쓰인 곳이 모두 바뀌어요. // "문제 카드를 컴포넌트로 만들어 줘"라고 하면 나중에 고치기가 훨씬 쉬워요.
상태 | 화면이 지금 이 순간 기억하고 있는 값이에요. 스위치가 켜졌는지, 점수가 몇 점인지, 몇 번째 문제인지 같은 거예요. // 상태가 바뀌면 화면도 따라서 다시 그려져요. // "새로고침하면 점수가 사라져요"는 상태를 따로 저장하지 않아서 생기는 일이에요.
변수 | 값을 넣어 두는, 이름표 붙은 상자예요. "점수 = 0"이라고 쓰면 '점수'라는 상자에 0을 넣은 거예요. // 상자 안의 값은 바꿀 수 있어서, 맞힐 때마다 "점수 = 점수 + 10"처럼 늘려요. // 이름표 덕분에 코드 여러 곳에서 같은 값을 꺼내 쓸 수 있어요.
함수 | 여러 번 하는 일을 한 묶음으로 만들고 이름을 붙인 거예요. "정답확인()"처럼요. // 한 번 만들어 두면 필요할 때마다 이름만 불러서 같은 일을 시킬 수 있어요. // 학급 규칙의 "아침 루틴"처럼, "아침 루틴 해요" 한마디로 여러 일을 순서대로 하는 것과 같아요.
이벤트 | 사용자가 한 행동이에요. 누르기, 입력하기, 스크롤, 키보드 누르기 같은 거예요. // 코드는 이벤트를 기다리다가 "버튼이 눌리면 → 다음 문제 보여 주기"처럼 반응해요. // 프롬프트에서 "언제"를 정확히 말하면(눌렀을 때, 다 입력했을 때) AI가 이벤트를 잘 연결해요.
조건문 | "만약 ~이면 이렇게, 아니면 저렇게" 하고 상황에 따라 다른 길로 가게 하는 코드예요. // "답이 맞으면 동그라미, 틀리면 다시 풀기"가 대표적인 조건문이에요. // 프롬프트에 "~이면 ~하고, 아니면 ~해 줘"라고 쓰면 그대로 조건문이 돼요.
반복문 | 같은 일을 여러 번 되풀이하게 하는 코드예요. // 학생 30명의 이름 카드를 하나씩 손으로 만들지 않고, "명단에 있는 사람마다 카드 하나씩"처럼 한 번에 만들어요. // 끝나는 조건이 잘못되면 영원히 돌아서 화면이 멈추기도 해요.
배열 | 여러 값을 순서대로 담아 둔 목록이에요. [사과, 배, 포도]처럼 써요. // 각 값에는 번호가 붙는데, 컴퓨터는 1이 아니라 0부터 세요. 그래서 사과가 0번이에요. // 문제 목록, 학생 명단, 단어장처럼 같은 종류가 여러 개일 때 배열에 담아요.
JSON | 데이터를 "이름": 값 짝으로 적는 약속된 형식이에요. {"이름": "민준", "점수": 90}처럼요. // 사람도 읽을 수 있고 컴퓨터도 쉽게 읽어서, 앱끼리 데이터를 주고받을 때 많이 써요. // 문제와 정답을 JSON으로 따로 정리해 두면, 코드는 그대로 두고 문제만 바꿔 넣을 수 있어요.
주석 | 코드 안에 사람이 보라고 적어 두는 메모예요. // 뒤에 있는 글은 컴퓨터가 실행하지 않고 건너뛰어요. // "여기서 정답을 확인해요" 같은 주석이 있으면 나중에 어디를 고쳐야 할지 찾기 쉬워요.
비동기 | 오래 걸리는 일을 기다리는 동안에도 화면이 멈추지 않게 하는 방식이에요. // 식당에서 주문하고 진동벨을 받으면, 음식이 나올 때까지 자리에서 다른 일을 할 수 있는 것과 같아요. // 서버에서 데이터를 가져오거나 파일을 올릴 때 쓰여요. 그래서 그동안 '불러오는 중' 표시를 보여 줘요.
랜덤 | 정해진 순서 없이 무작위로 하나를 고르는 거예요. // 문제 순서 섞기, 발표자 뽑기, 모둠 나누기에 써요. // 매번 결과가 달라서, 같은 퀴즈도 여러 번 새롭게 풀 수 있어요.
프레임워크 | 앱을 만드는 기본 틀과 규칙을 통째로 주는 도구예요. 리액트, Next.js가 그 예예요. // 집을 지을 때 기둥과 방 구조가 먼저 정해져 있고, 나는 방 안만 채우면 되는 것과 같아요. // 규칙을 따라야 하지만, 큰 앱도 정리된 모양으로 만들 수 있어요.
라이브러리 | 남이 미리 만들어 둔 기능을 골라 가져다 쓰는 코드 묶음이에요. // 공구함에서 필요한 공구만 꺼내 쓰는 것처럼, 차트 그리기, 날짜 계산, 반짝이 효과 같은 기능을 바로 쓸 수 있어요. // 프레임워크가 집의 뼈대라면, 라이브러리는 필요할 때 꺼내 쓰는 공구예요.
단일 HTML 파일 | 화면(HTML), 꾸밈(CSS), 기능(자바스크립트)을 파일 하나에 모두 넣은 웹앱이에요. // 파일 하나만 보내면 받은 사람이 두 번 눌러서 바로 열 수 있어서, 수업 도구로 나누기 정말 편해요. // 다만 화면과 기능이 많아지면 한 파일이 너무 길어져서 고치기 어려워져요.
리액트 프로젝트 | 화면을 버튼, 카드, 메뉴 같은 조각(컴포넌트)으로 나누고, 여러 파일에 정리해서 만드는 앱이에요. // 처음 준비가 조금 필요하지만, 화면이 많고 기능이 큰 앱도 정리된 상태로 키워 갈 수 있어요. // 이 사전도 리액트 프로젝트로 만들었어요.
패키지 설치 | 다른 사람이 만들어 둔 코드 묶음(패키지)을 내 프로젝트로 내려받는 거예요. 터미널에 npm install이라고 써요. // 앱을 처음 받았을 때 한 번 해 줘야 하고, 받은 묶음은 node_modules 폴더에 쌓여요. // "모듈을 찾을 수 없어요" 같은 오류가 나면 이걸 안 해서일 때가 많아요.

## 파일과 도구
폴더 구조 | 프로젝트 파일들을 어떤 폴더에 나눠 담았는지예요. // 그림은 images, 코드는 src처럼 서랍마다 종류를 정해 두면 찾기 쉬워요. // AI에게 "폴더 구조부터 보여 줘"라고 하면 전체 모습을 한눈에 알 수 있어요.
경로 | 파일이 있는 위치를 적은 주소예요. "images/cat.png"는 images 폴더 안의 cat.png라는 뜻이에요. // 학교에서 "3층 / 2학년 3반 / 사물함 5번"처럼 위치를 찾아가는 것과 같아요. // 그림이 안 뜨면 경로의 폴더 이름이나 철자가 조금 틀린 경우가 아주 많아요.
확장자 | 파일 이름 끝의 점 뒤에 붙은 부분이에요. .html, .png, .mp3처럼요. // 컴퓨터는 확장자를 보고 이 파일이 웹페이지인지, 그림인지, 소리인지 알아요. // 윈도우에서는 확장자가 숨겨져 있을 수 있어서, 보기 설정에서 '파일 확장명'을 켜 두면 편해요.
파일 이름 규칙 | 웹에 올릴 파일 이름은 영어 소문자, 숫자, 하이픈(-)만 쓰는 게 안전해요. 예: my-quiz-1.html // 한글이나 띄어쓰기, 대문자가 섞이면 내 컴퓨터에선 되는데 인터넷에 올리면 파일을 못 찾는 일이 생겨요. // 처음부터 규칙대로 지어 두면 그림 깨짐 같은 문제를 크게 줄일 수 있어요.
index.html | 사이트 주소로 들어오면 가장 먼저 열리는 첫 페이지 파일이에요. // 건물의 정문처럼, 주소 뒤에 파일 이름을 따로 안 써도 자동으로 이 파일을 열어요. // 그래서 첫 화면 파일의 이름은 꼭 index.html로 지어요.
README | 이 프로젝트가 무엇인지, 어떻게 쓰는지 적어 둔 설명서 파일이에요. 보통 README.md예요. // 깃허브에서 저장소를 열면 맨 아래에 자동으로 보여 줘요. // 다른 선생님과 나눌 때 사용법을 여기에 적어 두면 따로 설명할 필요가 줄어요.
코드 편집기 | 코드를 쓰고 고치는 전용 프로그램이에요. VS Code가 가장 많이 쓰여요. // 메모장과 달리 코드에 색을 입혀 읽기 쉽게 해 주고, 틀린 곳을 밑줄로 알려 줘요. // 폴더째 열어서 여러 파일을 한 번에 볼 수 있어요.
터미널 | 마우스 대신 글자로 명령을 써서 컴퓨터에 일을 시키는 창이에요. // "npm run dev"처럼 명령을 치고 Enter를 누르면 프로그램이 실행돼요. // 처음엔 낯설지만 바이브코딩에선 AI가 알려 준 명령을 복사해 붙여 넣기만 하면 될 때가 많아요.
개발자 도구 | 브라우저에서 F12를 누르면 열리는 점검 도구예요. // 오류를 보여 주는 콘솔, 휴대폰 크기로 보는 기기 모드, 화면 요소를 살펴보는 기능이 있어요. // 화면이 이상할 때 여기서 빨간 오류를 찾아 AI에게 보여 주면 빨리 고칠 수 있어요.
확장 프로그램 | 코드 편집기나 브라우저에 기능을 더해 주는 추가 프로그램이에요. // 스마트폰에 앱을 설치하듯 필요한 것만 골라 설치해요. 예를 들어 한국어 메뉴, 코드 자동 정리 같은 거예요. // 너무 많이 깔면 느려질 수 있어서 필요한 것만 쓰는 게 좋아요.

## 데이터와 저장
데이터베이스 | 정보를 표처럼 정리해 쌓아 두고, 필요할 때 꺼내 쓰는 인터넷 속 저장소예요. // 그래서 컴퓨터에서 쓴 내용을 휴대폰에서도, 다른 학생 기기에서도 똑같이 볼 수 있어요. // 학급 게시판, 출석부처럼 여러 사람이 함께 쓰는 기록이 필요할 때 써요. Supabase, Firebase가 대표적이에요.
CRUD | 데이터로 하는 기본 네 가지 일이에요. 만들기(Create), 읽기(Read), 고치기(Update), 지우기(Delete). // 학급 게시판이라면 글쓰기, 글 보기, 글 수정, 글 삭제가 바로 CRUD예요. // "CRUD 다 되게 해 줘"라고 하면 네 가지 기능을 모두 만들어 달라는 뜻이에요.
테이블·행·열 | 데이터베이스는 엑셀 표처럼 생긴 '테이블'에 정보를 담아요. // 가로 한 줄(행)은 학생 한 명처럼 한 건이고, 세로 한 줄(열)은 이름, 점수, 날짜처럼 항목이에요. // 출석부를 떠올리면 쉬워요. 한 줄이 한 학생, 한 칸이 하루예요.
스키마 | 표에 어떤 칸(열)이 있고, 각 칸에 무엇을 넣을지 정한 설계도예요. // "이름은 글자, 점수는 숫자, 날짜는 날짜"처럼 정해 두면 엉뚱한 값이 들어가지 않아요. // 데이터베이스를 만들기 전에 AI와 스키마부터 정하면 나중에 고칠 일이 줄어요.
로컬 스토리지 | 지금 쓰는 브라우저 안에 작게 저장해 두는 곳이에요. // 새로고침해도 점수나 설정이 남아 있지만, 다른 컴퓨터나 휴대폰에서는 안 보여요. 브라우저 기록을 지우면 사라져요. // 혼자 쓰는 연습장, 타이머 설정처럼 공유가 필요 없는 정보에 알맞아요.
스토리지 | 사진, 영상, 파일처럼 큰 자료를 올려 두는 창고예요. // 데이터베이스는 글과 숫자를 표로, 스토리지는 큰 파일을 통째로 보관해요. 데이터베이스에는 파일이 있는 위치만 적어 둬요. // 학생 작품 사진을 올리는 앱이라면 스토리지가 필요해요.
스프레드시트 DB | 구글 시트를 데이터베이스처럼 쓰는 방법이에요. // 앱에서 입력한 내용이 시트에 한 줄씩 쌓이고, 선생님은 익숙한 표 화면에서 바로 확인할 수 있어요. // 설정이 간단해서 작은 학급 앱에 좋지만, 사람이 많거나 보안이 중요하면 진짜 데이터베이스가 나아요.
CSV | 표를 쉼표(,)로 칸을 나눠 글자로만 적은 파일이에요. "이름,점수" 다음 줄 "민준,90"처럼요. // 엑셀이나 구글 시트에서 바로 열려서 표로 보여요. // 학생 명단이나 점수를 앱으로 가져오거나, 앱 결과를 내보낼 때 많이 써요.
API | 다른 서비스와 데이터를 주고받는 정해진 창구예요. // 식당 주문 창구처럼, 정해진 방식으로 주문하면(날씨 알려 줘) 그 서비스가 결과를 돌려줘요(오늘 맑음). // 날씨, 번역, 지도, AI 같은 기능을 내 앱에 붙일 때 API를 써요.
API 키 | API를 쓸 수 있게 해 주는 나만의 비밀 열쇠예요. 긴 영어와 숫자로 되어 있어요. // 이 열쇠로 누가 쓰는지 알아보고 사용량과 요금을 매겨요. // 화면 코드에 그대로 넣으면 누구나 볼 수 있어서 남이 내 돈으로 쓸 수 있어요. 그래서 환경 변수에 따로 숨겨요.
환경 변수 | API 키 같은 비밀 값을 코드 밖에 따로 보관하는 방법이에요. 보통 .env 파일에 적어요. // 코드에는 "열쇠는 금고에 있음"이라고만 쓰고, 진짜 열쇠는 금고(.env)에 둬요. // .env 파일은 깃허브에 올리지 않고, 배포할 때는 Vercel 같은 곳의 설정 화면에 따로 넣어요.
로그인·인증 | 앱에 들어온 사람이 누구인지 확인하는 기능이에요. // 아이디와 비밀번호, 또는 구글 계정으로 확인한 뒤, 그 사람에게 맞는 화면과 기록을 보여 줘요. // 학생마다 자기 기록이 따로 있어야 하면 로그인이 필요해요.
실시간 | 다른 사람이 바꾼 내용이 새로고침하지 않아도 내 화면에 바로 나타나는 거예요. // 단체 대화방에서 친구 메시지가 바로 뜨는 것처럼요. // 모둠 칠판, 실시간 투표처럼 여러 명이 동시에 쓰는 수업 도구에 꼭 필요해요.
백업 | 데이터를 다른 곳에 한 벌 더 복사해 두는 거예요. // 원본이 지워지거나 망가져도 복사본으로 되찾을 수 있어요. 학습지 원본을 USB에 따로 저장해 두는 것과 같아요. // 학기 말 기록처럼 잃어버리면 안 되는 자료는 정기적으로 백업해요.
동기화 | 컴퓨터, 휴대폰, 태블릿처럼 여러 기기의 내용을 똑같이 맞추는 거예요. // 한 기기에서 고치면 다른 기기에도 자동으로 같은 내용이 생겨요. // 구글 드라이브나 사진 앱이 동기화를 해 줘서 어느 기기에서나 같은 파일이 보여요.

## 보안과 개인정보
개인정보 | 이름, 얼굴 사진, 연락처, 주소처럼 누구인지 알 수 있는 정보예요. // 학생 정보는 특히 조심해야 해서, 앱에는 꼭 필요한 것만 받아요. 이름 대신 번호로 충분하면 번호만 받아요. // 개인정보를 모으는 앱이라면 저장 위치와 공개 범위를 꼭 확인해요.
익명화 | 실명 대신 번호나 별명으로 바꿔서 누구인지 모르게 하는 거예요. // "김민준" 대신 "학생 1"로 보여 주면, 결과를 함께 봐도 누가 누군지 알 수 없어요. // 설문 결과나 작품 전시처럼 여러 사람에게 보여 줄 때 좋아요.
HTTPS | 주소창에 자물쇠가 보이는 안전한 연결이에요. 주소가 https://로 시작해요. // 내 브라우저와 사이트가 주고받는 내용이 암호로 바뀌어서, 중간에 누가 엿봐도 알아볼 수 없어요. // Vercel 같은 곳에 배포하면 자동으로 HTTPS가 돼요.
접근 권한 | 누가 볼 수 있고, 누가 고치거나 지울 수 있는지 정하는 거예요. // "학생은 보기만, 선생님은 삭제도"처럼 역할마다 할 수 있는 일을 나눠요. // 권한을 안 나누면 학생이 실수로 다른 사람 글을 지울 수도 있어요.
행 수준 보안 | 데이터베이스 표에서 각자 자기 줄(행)만 보고 고칠 수 있게 막는 규칙이에요. RLS라고 해요. // 같은 표에 반 전체 기록이 있어도, 민준이는 민준이 기록만 볼 수 있어요. // Supabase를 쓴다면 이 규칙을 꼭 켜야 해요. 끄면 누구나 모든 기록을 볼 수 있어요.
비밀 키 노출 | API 키 같은 비밀 열쇠가 공개된 곳에 올라가서 남이 쓸 수 있게 된 사고예요. // 공개 저장소나 화면 코드에 키를 넣으면, 자동으로 키를 찾는 프로그램이 금방 가져가요. 요금이 나도 모르게 쌓일 수 있어요. // 노출됐다면 바로 그 키를 지우고(폐기) 새 키를 만들어요.
공개 저장소 | 깃허브에서 누구나 코드를 볼 수 있게 열어 둔 저장소예요. // 다른 선생님과 나누거나 무료 배포 도구를 쓸 때 편하지만, 안에 든 모든 파일이 공개돼요. // 그래서 API 키, 학생 이름, 사진은 절대 넣으면 안 돼요.
비공개 저장소 | 나와 내가 초대한 사람만 볼 수 있는 깃허브 저장소예요. // 학생 정보가 들어 있거나 아직 다듬는 중인 프로젝트는 비공개로 두는 게 안전해요. // 비공개여도 비밀 키는 환경 변수로 따로 두는 습관이 좋아요.

## 문제 해결
콘솔 | 개발자 도구(F12) 안에 있는, 오류와 메시지가 쌓이는 창이에요. // 화면에는 안 보이는 문제도 여기에는 빨간 글자(에러)나 노란 글자(경고)로 떠요. // 앱이 이상하면 콘솔부터 열어서 빨간 글자를 통째로 복사해 AI에게 주는 게 가장 빠른 방법이에요.
에러 메시지 | 무엇이, 어디서 잘못됐는지 알려 주는 글이에요. 보통 영어로 나와요. // 무섭게 보여도 "몇 번째 줄에서 무엇이 없어요" 같은 힌트가 들어 있어요. // 내 말로 풀어 쓰지 말고 통째로 복사해서 AI에게 붙여 넣으면 가장 정확하게 고쳐 줘요.
버그 | 만든 사람의 의도와 다르게 작동하는 문제예요. // 오류 없이 돌아가는데도 "맞혔는데 점수가 줄어요"처럼 결과가 틀리면 그것도 버그예요. // AI에게 말할 때는 "무엇을 했더니 → 이렇게 됐는데 → 원래는 이래야 해요" 순서로 알려 주면 좋아요.
디버깅 | 버그가 왜 생겼는지 찾아내서 고치는 과정이에요. // 의사가 증상을 보고 원인을 찾아 치료하는 것처럼, 언제 생기는지 확인하고 원인을 좁혀 가요. // AI와 함께라면 에러 메시지, 캡처, 재현 순서를 주는 게 디버깅의 절반이에요.
캐시 | 사이트를 빨리 열려고 브라우저가 예전 파일을 저장해 둔 거예요. // 덕분에 빠르지만, 파일을 고쳐도 브라우저가 예전 것을 보여 줘서 "반영이 안 돼요"가 생겨요. // 강력 새로고침(Ctrl+Shift+R)이나 시크릿 창으로 열면 캐시 문제인지 바로 알 수 있어요.
강력 새로고침 | 저장해 둔 예전 파일(캐시)을 무시하고 모든 파일을 새로 받아 오는 새로고침이에요. // 윈도우는 Ctrl+Shift+R, 맥은 Cmd+Shift+R이에요. // 고쳤는데 그대로일 때 가장 먼저 해 볼 일이에요.
로컬 서버 | 인터넷에 올리기 전에 내 컴퓨터 안에서만 앱을 열어 보는 방법이에요. 주소가 localhost로 시작해요. // 터미널에서 npm run dev를 하면 내 컴퓨터가 잠깐 작은 서버가 돼서 앱을 보여 줘요. // 내 컴퓨터에서만 열리고, 터미널을 끄면 같이 꺼져요. 다른 사람이 보려면 배포가 필요해요.

## 버전 관리
깃허브 | 코드를 인터넷에 저장하고, 바뀐 기록을 남기고, 여러 사람이 함께 작업하는 사이트예요. // 코드의 구글 드라이브 같은데, 언제 무엇을 바꿨는지 하나하나 기록이 남는 게 달라요. // Vercel 같은 배포 도구와 연결하면 올리기만 해도 사이트가 바뀌어요.
저장소 | 프로젝트 하나의 파일들과, 그동안 바뀐 기록을 모두 담은 보관함이에요. 레포(repo)라고도 해요. // 앱 하나에 저장소 하나씩 만들어요. // 저장소 안에서는 "어제 버튼 추가", "오늘 색 바꿈"처럼 지난 모습을 언제든 다시 볼 수 있어요.
커밋 | 지금까지 바꾼 내용을 하나의 기록으로 저장하는 거예요. 짧은 설명을 함께 붙여요. // 게임의 저장 지점처럼, 나중에 문제가 생기면 이 지점으로 돌아올 수 있어요. // "잘 될 때마다 커밋"하는 습관이 바이브코딩에서 가장 든든한 안전장치예요.
푸시 | 내 컴퓨터에서 만든 커밋을 깃허브로 올리는 거예요. // 커밋은 내 컴퓨터에만 있는 기록이고, 푸시해야 인터넷(깃허브)에도 생겨요. // 배포 도구와 연결돼 있으면 푸시하는 순간 사이트도 새로 만들어져요.
풀 | 깃허브에 있는 최신 내용을 내 컴퓨터로 가져오는 거예요. // 다른 사람이나 AI가 깃허브에 올린 변경을 내 컴퓨터에도 반영할 때 써요. // 작업을 시작하기 전에 먼저 풀을 하면, 예전 파일로 작업하는 실수를 막을 수 있어요.
클론 | 깃허브 저장소 전체를 내 컴퓨터로 처음 복사해 오는 거예요. // 풀이 '새로 바뀐 것만 가져오기'라면, 클론은 '처음 한 번 통째로 가져오기'예요. // 한 번 클론해 두면 그 다음부터는 풀만 하면 돼요.
포크 | 남의 저장소를 내 깃허브 계정으로 통째로 복사해 오는 거예요. // 원본은 그대로 두고, 내 복사본에서 마음대로 고쳐 볼 수 있어요. // 다른 선생님이 공개한 수업 도구를 내 반에 맞게 바꿔 쓰고 싶을 때 좋아요.
브랜치 | 원본은 그대로 두고, 갈래를 하나 나눠서 따로 실험하는 거예요. // 나뭇가지처럼 줄기(main)에서 갈라져 나온 곳에서 마음껏 고쳐도 원본은 안전해요. // 실험이 잘 되면 원본에 합치고(머지), 망하면 갈래만 버리면 돼요.
머지 | 따로 작업한 갈래(브랜치)를 원본에 합치는 거예요. // 실험 갈래에서 만든 새 기능이 원본 앱에 들어가게 돼요. // 합치기 전에 잘 되는지 확인하는 게 중요해요.
풀 리퀘스트 | "제가 이 갈래에서 고친 것을 원본에 합쳐 주세요" 하고 검토를 부탁하는 거예요. PR이라고 해요. // 무엇을 바꿨는지 한눈에 비교해 볼 수 있고, 함께 작업하는 사람이 확인한 뒤 합쳐요. // AI 코딩 도구가 작업을 끝내고 PR을 만들어 주면, 나는 내용을 보고 합칠지만 정하면 돼요.
충돌 | 두 사람(또는 두 갈래)이 같은 곳을 서로 다르게 고쳐서 자동으로 합칠 수 없는 상황이에요. // 한 사람은 제목을 "사과"로, 다른 사람은 "배"로 바꾸면 컴퓨터는 어느 쪽을 고를지 몰라요. // 이때는 사람이 둘 중 하나를 고르거나 섞어서 정해 줘야 해요. AI에게 맡겨도 돼요.
이슈 | 고칠 점, 새 아이디어, 할 일을 적어 두는 게시글이에요. 깃허브 저장소마다 있어요. // "버튼이 휴대폰에서 안 눌려요"처럼 하나씩 적어 두면 잊지 않고 차례대로 처리할 수 있어요. // 다른 사람이 내 앱의 문제를 알려 줄 때도 이슈로 남겨 줘요.

## 배포와 공유
배포 | 만든 웹앱을 인터넷에 올려서, 주소만 있으면 누구나 열 수 있게 하는 거예요. // 내 컴퓨터에서만 보이던 앱이 학생들 휴대폰에서도 열리게 돼요. // Vercel, Netlify, 깃허브 페이지 같은 도구로 무료로 할 수 있어요.
빌드 | 내가 쓴 여러 코드 파일을 인터넷에 올리기 좋은 최종 파일로 묶고 줄이는 과정이에요. // 이삿짐을 상자에 차곡차곡 포장하는 것처럼, 올리기 전에 한 번 정리해요. // 보통 배포 도구가 자동으로 해 줘서 직접 할 일은 많지 않아요.
빌드 오류 | 포장(빌드)하다가 문제가 생겨서 실패한 거예요. 그러면 배포도 안 돼요. // 내 컴퓨터에선 되는데 배포에서 실패하는 일도 흔해요. 파일 이름 대소문자나 빠진 설정 때문일 때가 많아요. // 배포 도구의 기록(로그)에서 빨간 줄을 통째로 복사해 AI에게 주면 돼요.
미리보기 배포 | 정식 주소에 올리기 전에, 시험용 주소에 먼저 올려 보는 거예요. // 바뀐 모습을 미리 확인하고 문제가 없으면 정식으로 내보내요. // 학생들이 쓰는 정식 사이트를 건드리지 않고 안전하게 시험할 수 있어요.
정식 배포 | 실제 사용자가 쓰는 진짜 주소에 올린 상태예요. 프로덕션이라고도 해요. // 여기 올라간 순간부터 학생들이 보는 화면이 바뀌어요. // 그래서 미리보기 배포로 충분히 확인한 다음 정식 배포를 해요.
호스팅 | 웹사이트 파일을 24시간 켜져 있는 컴퓨터(서버)에 올려 두고 보여 주는 서비스예요. // 가게를 열려면 건물 자리를 빌리듯, 사이트를 열려면 인터넷 속 자리를 빌려요. // Vercel, Netlify, 깃허브 페이지가 무료 호스팅을 해 줘요.
정적 사이트 | 서버에서 따로 계산하지 않고, 만들어 둔 파일만으로 보이는 사이트예요. // 받은 파일을 그대로 보여 주기만 해서 빠르고, 무료로 올리기도 쉬워요. // 이 사전처럼 데이터베이스 없이 정해진 내용을 보여 주는 사이트에 알맞아요.
도메인 | 웹사이트의 이름 주소예요. eunti.com처럼요. // 컴퓨터는 원래 숫자 주소로 찾아가는데, 외우기 쉽게 이름을 붙인 거예요. // 1년 단위로 돈을 내고 빌려 써요.
커스텀 도메인 | 배포 도구가 준 기본 주소(my-app.vercel.app) 대신 내가 산 주소(eunti.com)를 연결하는 거예요. // 사이트는 그대로고 주소만 짧고 기억하기 쉽게 바뀌어요. // 도메인을 산 곳과 배포 도구 양쪽에서 설정을 맞춰 줘야 해요.
파비콘 | 브라우저 탭 제목 옆에 보이는 작은 아이콘이에요. // 탭이 여러 개 열려 있어도 내 사이트를 한눈에 찾을 수 있게 해 줘요. // 정사각형 작은 그림 하나만 있으면 돼요. 이 사전은 파란 물음표예요.
링크 미리보기 | 카톡이나 문자로 주소를 보내면 자동으로 뜨는 그림, 제목, 설명이에요. OG 이미지라고도 해요. // 따로 정해 두지 않으면 밋밋한 주소만 보이거나 엉뚱한 그림이 떠요. // 학부모나 학생에게 링크를 보낼 일이 많다면 꼭 만들어 두면 좋아요.
QR 코드 | 휴대폰 카메라로 찍으면 정해진 주소로 바로 이동하는 네모 무늬예요. // 긴 주소를 학생들이 하나하나 칠 필요가 없어요. 칠판이나 학습지에 붙여 두면 편해요. // 주소만 있으면 무료 사이트에서 금방 만들 수 있어요.
오픈소스 라이선스 | 남이 공개한 코드, 글꼴, 그림을 어디까지 써도 되는지 정한 약속이에요. // "써도 돼요, 고쳐도 돼요, 대신 출처는 밝혀요"처럼 조건이 붙어 있어요. MIT, CC BY가 흔해요. // 가져다 쓸 때는 라이선스를 확인하고, 필요하면 사이트 아래에 출처를 적어요.

## 속도
로딩 속도 | 주소를 누른 뒤 사이트가 다 열리기까지 걸리는 시간이에요. // 3초만 넘어가도 기다리기 답답해서 떠나는 사람이 많아요. 학교 와이파이는 느릴 때도 많아요. // 그림 크기를 줄이고, 꼭 필요한 것만 먼저 불러오면 빨라져요.
이미지 최적화 | 그림이 보기에는 그대로인데 파일 크기만 확 줄이는 거예요. // 휴대폰 사진 한 장이 5MB라면, 웹용으로 줄이면 300KB로도 충분히 선명해요. // WebP 형식으로 바꾸거나 화면에 보이는 크기에 맞춰 줄이면 사이트가 훨씬 빨라져요.
지연 로딩 | 그림을 처음부터 다 불러오지 않고, 스크롤해서 화면에 보일 때가 돼서야 불러오는 거예요. // 아직 안 볼 그림을 미리 받지 않으니 첫 화면이 빨리 떠요. // 그림이 많은 갤러리나 긴 목록에 특히 좋아요.
용량 | 파일이 차지하는 크기예요. KB < MB < GB 순서로 커져요. // 용량이 클수록 받는 데 오래 걸리고, 휴대폰 데이터도 많이 써요. // 글은 아주 작고, 사진은 크고, 영상은 훨씬 커요. 웹에는 가능한 한 작게 올리는 게 좋아요.

## 기획과 요청
프롬프트 | AI에게 무엇을 해 달라고 쓰는 요청 글이에요. // AI는 내 머릿속을 볼 수 없어서, 쓴 글만 보고 만들어요. 그래서 같은 것을 원해도 어떻게 쓰느냐에 따라 결과가 크게 달라요. // "언제 + 어디서 + 무엇이 + 어떻게"를 넣고, 이 사전에 나온 정확한 이름을 쓰면 원하는 결과에 훨씬 가까워져요.
좋은 프롬프트 4요소 | 좋은 요청에는 네 가지가 들어가요. 누가 쓰는지(초등 3학년), 무엇을 만들지(받아쓰기 퀴즈), 어떤 모양인지(큰 글자, 파란색), 무엇은 하지 말지(광고·로그인 없이). // 이 네 가지가 빠지면 AI가 빈칸을 마음대로 채워요. // 처음 요청할 때 네 줄로 적어 보는 연습을 하면 금방 익숙해져요.
PRD | 무엇을, 누구를 위해, 어떤 기능으로 만들지 정리한 짧은 기획서예요. 제품 요구사항 문서의 줄임말이에요. // 수업 지도안처럼 목표, 대상, 순서를 미리 적어 두는 거예요. // 큰 앱을 만들 때는 AI와 PRD부터 함께 쓰고, 그걸 보면서 화면을 하나씩 만들면 길을 잃지 않아요.
와이어프레임 | 색과 그림 없이 회색 상자와 선만으로 화면 배치를 그린 밑그림이에요. // 집을 짓기 전 평면도처럼, 무엇이 어디에 올지만 정해요. // 모양보다 구조를 먼저 정할 수 있어서, "와이어프레임부터 보여 줘"라고 하면 방향을 빨리 맞출 수 있어요.
목업 | 색, 글꼴, 그림까지 입혀서 진짜 화면처럼 보이게 만든 그림이에요. 다만 눌러도 움직이지는 않아요. // 와이어프레임이 연필 밑그림이라면, 목업은 색칠까지 끝난 완성 그림이에요. // 디자인 느낌을 확인하고 정하는 데 써요.
프로토타입 | 화면들을 이어 놓아서 실제로 눌러 볼 수 있게 만든 시험용 앱이에요. // 진짜 데이터나 저장은 없어도 "이 버튼을 누르면 다음 화면"이 작동해요. // 학생에게 먼저 써 보게 하고 불편한 곳을 찾을 때 좋아요.
레퍼런스 | 원하는 느낌을 보여 주려고 가져온 참고 그림이나 사이트예요. // "깔끔하게"라는 말보다 "이 사이트처럼"이 AI에게 훨씬 정확하게 전해져요. // 캡처를 함께 올리고 "색은 이것처럼, 배치는 저것처럼"처럼 어떤 점을 참고할지 짚어 주면 좋아요.
디자인 시스템 | 색, 글꼴, 버튼 모양, 여백 같은 디자인 규칙을 한곳에 정리해 둔 모음이에요. // 학교 교복 규정처럼 정해 두면, 화면이 많아져도 모두 한 학교처럼 통일돼 보여요. // AI에게 처음에 디자인 시스템을 알려 주면 새 화면을 만들 때도 같은 모습을 지켜요.
디자인 토큰 | 디자인 규칙의 값에 붙인 이름이에요. "주요색 = #0095FF", "큰 여백 = 24px"처럼요. // 이름으로 쓰기 때문에, 주요색 값만 바꾸면 앱 전체의 파란색이 한 번에 바뀌어요. // 색을 하나하나 고칠 필요가 없어서 디자인을 바꾸기 쉬워요.
유저 플로우 | 사용자가 첫 화면에서 목표까지 거쳐 가는 화면 순서예요. // "시작 → 이름 쓰기 → 문제 풀기 → 결과 보기"처럼 화살표로 이어 그려요. // 플로우를 먼저 정하면 빠진 화면이나 막다른 길을 미리 찾을 수 있어요.
접근성 | 눈이 잘 안 보이거나, 손이 불편하거나, 소리를 못 듣는 사람도 똑같이 쓸 수 있게 만드는 거예요. // 글자 대비를 높이고, 키보드로도 움직일 수 있게 하고, 그림에 설명을 붙이는 것들이 포함돼요. // 특수교육에서는 특히 중요해요. 접근성을 챙기면 결국 모든 학생이 더 쓰기 편해져요.
대체 텍스트 | 그림을 볼 수 없는 사람에게 화면 읽기 프로그램이 대신 읽어 주는 그림 설명이에요. alt라고 해요. // "사과 그림"처럼 그림이 무엇을 뜻하는지 짧게 적어요. // 그림이 안 떴을 때도 이 글이 대신 보여서, 무엇이 있던 자리인지 알 수 있어요.
예시 주기 | 원하는 결과를 말로 설명하는 것과 함께 "이런 식으로" 하고 예를 한두 개 보여 주는 거예요. // "문제는 이렇게: 사과 → 🍎"처럼 예를 주면 AI가 형식과 말투를 그대로 따라 해요. // 문제 만들기, 피드백 문구 쓰기처럼 비슷한 걸 여러 개 만들 때 효과가 커요.
제약 조건 | 꼭 지켜야 할 조건을 미리 말해 두는 거예요. "버튼은 3개까지", "광고 없이", "인터넷 없이도 되게"처럼요. // 말하지 않으면 AI가 편한 대로 만들어서 다시 고쳐야 해요. // 하지 말아야 할 것을 적는 것도 제약 조건이에요.
체크리스트 확인 | 다 만들었는지 확인할 기준을 목록으로 정리한 거예요. // "□ 휴대폰에서도 잘 보임 □ 새로고침해도 점수 남음"처럼 적어 두고, 마지막에 AI에게 하나씩 점검해 달라고 해요. // 빠뜨린 기능을 찾아내기 좋아요.

## 작업 흐름
계획 먼저 | 바로 만들라고 하지 않고, "어떻게 만들지 계획부터 보여 줘"라고 먼저 요청하는 거예요. // 계획을 보고 방향이 맞는지 확인한 뒤 만들게 하면, 엉뚱하게 다 만들어 놓고 다시 하는 일을 줄일 수 있어요. // 큰 작업일수록 효과가 커요.
작게 나눠 요청 | 앱 전체를 한 번에 시키지 않고, 화면 하나, 기능 하나씩 나눠서 부탁하는 거예요. // 한 번에 많이 시키면 빠뜨리거나 꼬이기 쉽고, 어디가 잘못됐는지 찾기도 어려워요. // 하나 만들고 확인하고, 다음 것을 부탁하는 순서가 가장 안전해요.
반복 수정 | 만들고 → 눌러 보고 → 고치기를 여러 번 되풀이하며 완성해 가는 방식이에요. // 처음부터 완벽한 결과를 기대하기보다, 조금씩 다듬어 가는 게 바이브코딩의 기본이에요. // 한 번에 한두 가지만 고쳐 달라고 하면 더 잘 고쳐져요.
스크린샷 피드백 | 화면을 캡처해서 보여 주며 "여기 이 부분"을 고쳐 달라고 하는 방법이에요. // "위쪽 버튼이 좀 이상해요"보다 그림 한 장이 훨씬 정확해요. // 캡처 위에 동그라미를 그리거나 "빨간 동그라미 부분"처럼 짚어 주면 더 좋아요.
에러 붙여 넣기 | 오류가 났을 때 내 말로 설명하지 않고, 에러 메시지를 통째로 복사해서 붙여 넣는 거예요. // 에러 메시지에는 원인과 위치가 정확히 적혀 있어서, AI가 바로 고칠 곳을 찾아요. // 콘솔(F12)의 빨간 글자를 처음부터 끝까지 복사해요.
잘 될 때 저장 | 앱이 잘 작동할 때마다 그 상태를 따로 저장해 두는 거예요. 커밋하거나 파일을 복사해 둬요. // 다음 수정에서 망가져도 마지막으로 잘 되던 모습으로 바로 돌아올 수 있어요. // "잘 되네!" 하는 순간이 저장할 때예요.
되돌리기 | 고친 뒤 문제가 생기면, 잘 되던 예전 버전으로 돌아가는 거예요. // 망가진 걸 계속 고치다 보면 더 꼬일 때가 많아서, 차라리 돌아가서 다시 시도하는 게 빠를 때가 있어요. // 잘 될 때 저장해 둬야 되돌릴 곳이 생겨요.
리팩토링 | 겉모습과 기능은 그대로 두고, 코드 속만 깔끔하게 정리하는 거예요. // 방 정리처럼, 물건은 다 그대로인데 찾기 쉽게 정리하는 거예요. // 코드가 너무 길고 복잡해져서 AI도 자꾸 실수할 때 "기능은 그대로 두고 리팩토링해 줘"라고 해요.
새 대화로 시작 | 대화가 너무 길어지면 AI가 앞부분을 잊거나 헷갈려요. 그럴 때 새 대화로 옮기는 거예요. // 지금까지의 요약과 최신 코드를 들고 새 대화를 시작하면 다시 또렷하게 작업할 수 있어요. // "지금까지 한 일을 새 대화에 붙여 넣을 수 있게 요약해 줘"라고 먼저 부탁하면 편해요.

## AI 도구 이해하기
채팅형 | AI가 대화창에 코드를 답으로 써 주면, 내가 그걸 복사해서 파일에 붙여 넣는 방식이에요. // 시작하기 쉽지만, 복사·붙여 넣기와 실행 확인은 내가 직접 해야 해요. // 코드가 길면 "전체 코드로 줘"라고 해야 빠진 부분 없이 받을 수 있어요.
에이전트형 | AI가 내 파일을 직접 열어서 만들고, 고치고, 실행해서 확인까지 하는 방식이에요. // 나는 원하는 것을 말하고, AI가 한 일을 확인하고 승인하면 돼요. // 일이 빠르지만, AI가 무엇을 바꿨는지 꼭 확인하고 잘 될 때 저장하는 습관이 필요해요.
코딩 에이전트 | 파일 읽기, 고치기, 명령 실행을 스스로 이어서 하는 AI예요. Claude Code가 그 예예요. // "로그인 기능 넣어 줘"라고 하면 필요한 파일을 찾고, 고치고, 실행해서 확인하는 여러 단계를 알아서 해요. // 그래도 방향은 내가 정해야 해서, 계획을 먼저 보여 달라고 하면 좋아요.
모델 | AI의 두뇌 종류예요. 같은 회사의 AI도 여러 모델이 있어요. // 빠르고 가벼운 모델, 느리지만 깊게 생각하는 모델처럼 성격이 달라요. // 간단한 일은 빠른 모델로, 복잡한 앱이나 어려운 오류는 깊게 생각하는 모델로 고르면 좋아요.
토큰 | AI가 글을 읽고 쓸 때 쓰는 작은 조각 단위예요. 한글 한두 글자가 대략 토큰 하나예요. // 사용량, 요금, 대화 길이 한도가 모두 토큰으로 계산돼요. // 긴 코드를 여러 번 주고받으면 토큰을 많이 써서 한도에 빨리 닿아요.
컨텍스트 | AI가 지금 대화에서 기억하고 참고하는 내용 전체예요. 내 요청, AI 답, 올린 파일이 모두 들어가요. // 담을 수 있는 양이 정해져 있어서, 대화가 너무 길면 앞부분을 잊어버려요. // 중요한 규칙은 프로젝트 지침에 넣거나 새 대화에서 다시 알려 주면 좋아요.
프로젝트 지침 | 매번 말하지 않아도 AI가 그 프로젝트에서 늘 지키는 규칙이에요. // "말투는 ~해요, 색은 파란색 계열, 학생 이름은 저장하지 않기"처럼 적어 두면 새 대화에서도 알아서 지켜요. // 이 사전의 CLAUDE.md 파일이 바로 프로젝트 지침이에요.
멀티모달 | 글뿐 아니라 그림, 화면 캡처, 파일, 목소리까지 함께 알아듣는 AI예요. // 손으로 그린 화면 스케치를 사진으로 올리고 "이렇게 만들어 줘"라고 할 수 있어요. // 말로 설명하기 어려운 건 그림으로 보여 주는 게 빨라요.
커넥터 | AI가 노션, 구글 드라이브, 피그마 같은 다른 서비스에 연결해서 직접 읽고 쓰게 하는 통로예요. MCP라고도 해요. // 연결해 두면 "노션 계획서를 읽고 앱을 만들어 줘"처럼 복사·붙여 넣기 없이 일할 수 있어요. // 무엇에 접근하게 할지 내가 정하고, 필요한 것만 연결하는 게 안전해요.
할루시네이션 | AI가 없는 사실이나 없는 기능을 진짜처럼 그럴듯하게 지어내는 거예요. // 자신 있게 말해도 틀릴 수 있어서, "이 도구에 그런 기능이 있어?"처럼 중요한 건 직접 확인해요. // 특히 사람 이름, 날짜, 출처, 버튼 위치 같은 구체적인 내용은 한 번 더 확인해요.

## 보기 쉽게
시각적 위계 | 화면에서 무엇을 먼저 보고, 무엇을 나중에 볼지 크기와 진하기로 정해 주는 거예요. // 신문의 큰 제목 → 작은 제목 → 본문 순서처럼, 중요한 것일수록 크고 진하게 해요. // 모든 게 다 크고 진하면 오히려 아무것도 눈에 안 들어와요.

정렬 | 글과 상자들의 왼쪽 끝이나 가운데를 한 줄로 맞추는 거예요. // 줄이 맞으면 깔끔하고 믿음직해 보이고, 들쭉날쭉하면 어수선해 보여요. // 긴 글은 왼쪽 정렬이 가장 읽기 쉬워요.

가독성 | 글이 얼마나 편하게 읽히는지예요. // 글자 크기, 줄 간격, 한 줄 길이, 글자와 배경의 대비가 가독성을 정해요. // 프로젝터로 보여 주거나 저학년이 쓴다면 글자를 더 크게, 줄 간격을 더 넓게 해요.
인지 부하 | 화면을 보고 한 번에 생각하고 기억해야 하는 양이에요. // 버튼이 너무 많거나, 설명이 길거나, 규칙이 복잡하면 머리가 금방 지쳐요. // 한 화면에 한 가지 일만, 꼭 필요한 것만 보여 주면 부담이 줄어요. 특수교육에서 특히 중요해요.
점진적 공개 | 처음에는 꼭 필요한 것만 보여 주고, 더 알고 싶을 때 펼쳐 보게 하는 거예요. // 이 사전의 [자세히 보기]가 바로 점진적 공개예요. // 처음 쓰는 사람도 겁먹지 않고, 익숙한 사람은 더 깊이 볼 수 있어요.

힉의 법칙 | 고를 수 있는 게 많을수록 고르는 데 시간이 오래 걸린다는 법칙이에요. // 메뉴가 20개면 하나를 찾는 데 한참 걸리지만, 4개면 금방 골라요. // 선택지를 줄이거나 묶어서 보여 주면 더 빨리 결정할 수 있어요.
기본값 | 처음부터 미리 골라져 있는 값이에요. // 대부분 사람이 고를 값을 미리 골라 두면, 그대로 넘어가도 돼서 편해요. 예: 글자 크기 '보통', 효과음 '켜짐'. // 하지만 원하지 않는 걸 몰래 골라 두면 다크 패턴이 돼요.
오류 예방 | 실수가 일어난 뒤 고치는 것보다, 실수 자체를 미리 막는 거예요. // 날짜는 직접 쓰는 대신 달력에서 고르게 하고, 지우기 전에 "정말 지울까요?"라고 한 번 더 물어요. // 잘못 입력할 틈을 줄이면 사용자도 덜 당황해요.

다크 패턴 | 사용자를 속이거나 헷갈리게 해서 원하지 않는 걸 고르게 만드는 나쁜 설계예요. // "거절" 버튼을 아주 작고 흐리게 숨기거나, 몰래 구독에 체크해 두는 것들이에요. // 학생과 학부모가 쓰는 앱에서는 절대 쓰지 않아요. 고르기 쉽고 공정하게 보여 줘요.

## 사용자 이해하기
사용성 | 사람들이 얼마나 쉽게, 빠르게, 실수 없이 쓸 수 있는지예요. // 예뻐도 어떻게 쓰는지 헷갈리면 사용성이 낮은 거예요. // 설명 없이 처음 써 봐도 바로 할 수 있다면 사용성이 높은 앱이에요.
페르소나 | 이 앱을 쓸 대표 사용자를 진짜 한 사람처럼 구체적으로 그려 본 가상 인물이에요. // "민준, 2학년, 한글을 막 배우는 중, 태블릿을 씀"처럼 정하면 디자인 결정을 하기 쉬워져요. // AI에게도 페르소나를 알려 주면 그 사람에게 맞는 글자 크기와 말투로 만들어요.
사용자 여정 | 사용자가 앱을 처음 알게 된 순간부터 다 쓰고 끝낼 때까지 겪는 일의 흐름이에요. // QR 찍기 → 들어오기 → 활동하기 → 결과 보기처럼 단계마다 무엇을 느끼는지도 함께 생각해요. // 어디서 막히거나 지루해하는지 미리 찾을 수 있어요.
정보 구조 | 메뉴와 내용을 어떻게 나누고 묶고 이름 붙일지 정한 지도예요. // 도서관이 책을 분야별로 나눠 꽂아 두어야 찾기 쉬운 것과 같아요. // 화면이 많은 앱일수록 정보 구조를 먼저 정해야 사람들이 길을 잃지 않아요.
사용성 테스트 | 실제 사용자가 앱을 써 보는 모습을 옆에서 보며 불편한 곳을 찾는 거예요. // 만든 사람 눈에는 당연한 것도, 처음 쓰는 학생은 어디를 눌러야 할지 모를 수 있어요. // 도와주지 말고 지켜보기만 하는 게 중요해요. 두세 명만 해 봐도 큰 문제는 다 보여요.

매거진 | 잡지처럼 크고 작은 사진과 글을 섞어 리듬감 있게 놓는 배치예요. // 중요한 기사는 크게, 나머지는 작게 놓아 보는 재미가 있어요. // 학급 소식지나 행사 소개 페이지에 좋아요.

## 꾸밈 속성
안쪽 여백 | 상자 테두리와 그 안의 내용 사이 빈 공간이에요. 패딩이라고도 해요. // 액자 속 그림 둘레의 여백처럼, 넉넉하면 내용이 답답하지 않아 보여요. // 버튼 안쪽 여백을 늘리면 버튼이 커져서 누르기도 쉬워요.
바깥 여백 | 상자 바깥쪽, 옆 상자와의 사이를 띄우는 빈 공간이에요. 마진이라고도 해요. // 안쪽 여백은 상자 안, 바깥 여백은 상자 밖이에요. // 상자끼리 너무 붙어 있으면 바깥 여백을 늘려 달라고 해요.
간격 | 나란히 놓인 여러 요소 사이를 똑같이 벌리는 거리예요. 갭이라고도 해요. // 카드 사이, 버튼 사이를 한꺼번에 같은 거리로 맞출 때 써요. // "카드 간격을 16px로"처럼 숫자로 말하면 정확해요.
모서리 둥글기 | 상자 모서리를 얼마나 둥글게 깎을지예요. // 0이면 각진 네모, 조금 주면 부드러운 네모, 끝까지 주면 알약이나 동그라미가 돼요. // 둥글수록 친근하고 부드러워 보여요.
테두리 | 상자 가장자리에 두르는 선이에요. // 두께, 색, 실선·점선을 정할 수 있어요. // 선택된 칸을 파란 테두리로 표시하는 것처럼 상태를 보여 줄 때도 써요.
그림자 | 상자 아래에 그림자를 깔아서 바닥에서 붕 떠 보이게 하는 효과예요. // 그림자가 진하고 넓을수록 더 높이 떠 보여요. // 마우스를 올렸을 때 그림자를 키우면 '누를 수 있다'는 느낌이 나요.
투명도 | 얼마나 비쳐 보일지를 정해요. 0이면 완전히 안 보이고, 1이면 꽉 차 보여요. // 0.5면 반쯤 비쳐서 뒤가 보여요. // 지금 못 누르는 버튼을 흐리게 보여 줄 때 자주 써요.
블러 | 뿌옇게 흐리게 만드는 효과예요. // 김 서린 유리처럼 뒤를 흐리게 하면 앞의 내용이 더 잘 보여요. // 팝업 뒤 배경을 흐리게 하거나, 유리 느낌을 낼 때 써요.
그라데이션 | 한 색에서 다른 색으로 스르르 바뀌는 칠하기예요. // 하늘이 위는 진하고 아래는 연한 것처럼 부드러운 변화를 줘요. // 너무 많은 색을 섞으면 촌스러워 보일 수 있어 비슷한 색끼리 써요.
구분선 | 내용과 내용 사이를 나누는 가는 선이에요. // 목록 항목 사이, 메뉴 묶음 사이에 넣으면 구역이 분명해져요. // 선 대신 여백만으로도 나눌 수 있어서, 너무 많이 쓰지 않는 게 좋아요.

## 색과 글자
주요색 | 사이트를 대표하는 색이에요. 프라이머리 컬러라고도 해요. // 가장 중요한 버튼, 선택 표시, 링크에 써서 "여기를 보세요"라고 알려 줘요. // 이 사전의 주요색은 루미너스 블루(#0095FF)예요.
강조색 | 꼭 눈에 띄어야 할 곳에만 조금 쓰는 색이에요. // 형광펜처럼 아껴 써야 효과가 있어요. 여기저기 쓰면 아무것도 강조되지 않아요. // 주요색과 잘 어울리는 반대 느낌의 색을 고르기도 해요.
색 팔레트 | 이 사이트에서 쓸 색을 미리 몇 가지로 정해 둔 물감 세트예요. // 주요색, 강조색, 배경색, 글자색처럼 역할을 나눠요. // 팔레트를 정해 두면 화면이 많아져도 색이 통일돼요.
색 코드 | 색을 #0095FF처럼 숫자와 영어로 적은 이름이에요. // "파란색"은 사람마다 다르게 떠올리지만, 색 코드는 딱 하나의 색이에요. // AI에게 색을 정확히 말하고 싶을 때 색 코드를 함께 적어요.
대비 | 글자와 배경의 밝기 차이예요. // 차이가 크면(흰 바탕에 검은 글자) 잘 보이고, 작으면(연회색 바탕에 흰 글자) 잘 안 보여요. // 눈이 불편한 사람과 프로젝터를 위해 대비를 충분히 높여요.
글자 굵기 | 글자가 얼마나 굵은지예요. 숫자로 100(아주 가늘게)부터 900(아주 굵게)까지 있어요. // 보통 본문은 400, 제목은 700을 써요. // 굵기 차이로 중요한 것과 덜 중요한 것을 나눠요.
글자 크기 | 글자가 얼마나 큰지예요. 보통 px 단위로 말해요. // 휴대폰 본문은 16px 이상이 읽기 편하고, 어린 학생이나 프로젝터는 더 크게 해요. // "제목은 32px, 본문은 18px"처럼 숫자로 말하면 정확해요.
줄 간격 | 윗줄과 아랫줄 사이의 거리예요. // 너무 좁으면 줄이 붙어서 읽기 힘들고, 글자 크기의 1.5배쯤이면 편해요. // 글이 많은 화면이라면 줄 간격을 넉넉하게 해 달라고 해요.
자간 | 글자와 글자 사이의 거리예요. // 큰 제목은 살짝 좁히면 단단해 보이고, 작은 영어 대문자는 살짝 넓히면 읽기 쉬워요. // 한글 본문은 보통 그대로 두는 게 좋아요.
말줄임 | 글이 길어서 칸을 넘칠 때 뒤를 "…"로 줄여 보여 주는 거예요. // 카드 제목처럼 칸 크기가 정해진 곳에서 모양이 깨지지 않게 해 줘요. // 한 줄 또는 두 줄까지 보여 주고 줄일지 정할 수 있어요.
웹폰트 | 인터넷에서 불러와서 쓰는 글꼴이에요. // 컴퓨터에 그 글꼴이 깔려 있지 않아도 누구에게나 같은 글꼴로 보여요. // 이 사전은 Pretendard라는 웹폰트를 써요. 무료로 쓸 수 있는지 라이선스를 확인해요.

## 그림과 파일 형식
PNG | 배경을 투명하게 할 수 있는 그림 파일 형식이에요. // 캐릭터, 아이콘, 로고처럼 배경 없이 다른 화면 위에 얹을 그림에 좋아요. // 사진을 PNG로 저장하면 파일이 커지니까 사진은 JPG를 써요.
JPG | 사진에 잘 맞는 가벼운 그림 파일 형식이에요. // 색이 많은 사진도 작은 크기로 저장할 수 있지만, 투명 배경은 안 돼요. // 너무 많이 압축하면 사진이 뭉개질 수 있어요.
SVG | 선과 도형 정보로 저장한 그림 파일이라 아무리 키워도 깨지지 않아요. // 아이콘, 로고, 단순한 그림에 좋고, 코드로 색을 바꾸기도 쉬워요. // 사진처럼 복잡한 그림에는 맞지 않아요.
WebP | 화질은 비슷하면서 JPG, PNG보다 용량이 작은 인터넷용 그림 형식이에요. // 투명 배경도 되고, 사이트를 빠르게 열리게 해 줘요. // 요즘 웹사이트에 그림을 올릴 때 많이 써요.
벡터 | 그림을 "여기서 저기까지 선, 이 안은 파란색"처럼 선과 도형 정보로 저장한 거예요. // 크게 키워도 다시 계산해서 그리기 때문에 언제나 선명해요. // 로고, 아이콘, 도형 그림에 좋아요. SVG가 대표적인 벡터 파일이에요.
비트맵 | 그림을 아주 작은 색 점(픽셀)을 촘촘히 모아 만든 거예요. // 사진처럼 복잡한 색을 담기 좋지만, 크게 키우면 점이 커져서 흐리고 계단처럼 보여요. // JPG, PNG, WebP가 비트맵 파일이에요.
투명 배경 | 그림 뒤가 비어 있어서 어떤 바탕 위에 올려도 자연스러운 거예요. // 스티커를 공책에 붙이듯, 흰 네모 없이 그림만 놓여요. // 투명 배경이 필요하면 PNG나 WebP로 저장해요.
해상도 | 그림을 이루는 점(픽셀)의 개수예요. 가로 × 세로로 말해요. // 점이 많을수록 선명하지만 파일이 커져요. // 화면에 보이는 크기보다 너무 큰 그림은 줄여서 올리면 빨라져요.
비율 | 그림이나 화면의 가로와 세로의 비예요. // 16:9는 TV와 영상, 4:3은 옛날 화면, 1:1은 정사각형이에요. // 카드 사진 비율을 정해 두면 목록이 반듯하게 정리돼 보여요.
잘라 맞추기 | 정해진 칸을 빈틈없이 꽉 채우려고, 그림의 가장자리를 잘라 내는 방식이에요. 커버(cover)라고 해요. // 칸은 깔끔하게 채워지지만 그림 끝이 잘릴 수 있어요. // 카드 사진, 배경 사진처럼 모양이 중요할 때 써요.
전체 보이기 | 그림이 하나도 잘리지 않게 칸 안에 다 넣는 방식이에요. 컨테인(contain)이라고 해요. // 그림 비율이 칸과 다르면 위아래나 양옆에 빈칸이 생겨요. // 학생 작품, 지도처럼 잘리면 안 되는 그림에 써요.
에셋 | 앱을 만드는 데 쓰는 그림, 소리, 글꼴, 아이콘 같은 재료 파일들이에요. // 요리 재료처럼 미리 모아 두고 코드에서 불러다 써요. // 보통 assets라는 폴더에 정리해요.
스프라이트 | 움직이는 그림의 여러 장면을 한 장에 나란히 모아 둔 그림이에요. // 장면을 하나씩 차례로 보여 주면 플립북처럼 움직여 보여요. // 게임 캐릭터가 걷거나 뛰는 모습을 만들 때 써요.
이모지 | 😀처럼 글자처럼 입력하는 작은 그림 문자예요. // 따로 그림 파일이 없어도 글자처럼 쓸 수 있어서 편해요. // 다만 기기마다 모양이 조금씩 달라서, 정확한 모양이 중요하면 아이콘을 써요.

## 입력 폼

체크박스 | 네모 칸에 체크해서 여러 개를 동시에 고를 수 있는 부품이에요. // "좋아하는 과목을 모두 고르세요"처럼 여러 개를 고를 때 써요. // 하나만 골라야 한다면 라디오를 써요.

슬라이더 | 막대 위 손잡이를 좌우로 밀어서 값을 정하는 부품이에요. // 볼륨, 밝기, 글자 크기처럼 정확한 숫자보다 '이쯤'이 중요할 때 좋아요. // 정확한 숫자가 필요하면 옆에 숫자를 같이 보여 줘요.

피커 | 날짜, 시간, 색처럼 정해진 것 중 하나를 고르게 해 주는 부품을 통틀어 부르는 말이에요. // 바퀴를 돌리는 모양, 달력 모양, 색판 모양 등 여러 가지가 있어요. // "날짜 피커", "시간 피커"처럼 앞에 무엇을 고르는지 붙여 말하면 정확해요.
플레이스홀더 | 입력 칸이 비어 있을 때 흐리게 보이는 예시 글이에요. "예: 홍길동"처럼요. // 쓰기 시작하면 사라져요. // 사라지면 무엇을 쓰는 칸이었는지 잊을 수 있어서, 중요한 설명은 라벨로 따로 둬요.
텍스트 영역 | 여러 줄을 쓸 수 있는 큰 입력 칸이에요. // 소감, 일기, 건의 사항처럼 긴 글을 쓸 때 써요. // 글자 수 제한이 있다면 "120/200"처럼 남은 글자 수를 보여 주면 친절해요.
라벨 | 입력 칸 위나 옆에 붙은 이름표예요. "이름", "학년"처럼요. // 무엇을 쓰는 칸인지 늘 보여 줘서 헷갈리지 않아요. // 화면 읽기 프로그램도 라벨을 읽어 주기 때문에 접근성에도 꼭 필요해요.

## 버튼

눌림 | 버튼을 꾹 누르고 있는 동안의 모습이에요. // 살짝 작아지거나 진해져서 진짜 버튼을 누른 듯한 느낌을 줘요. // 누른 느낌이 있으면 눌렸는지 헷갈리지 않아요.

비활성 | 지금은 누를 수 없어서 흐리게 보이는 버튼이에요. // 예를 들어 이름을 다 쓰기 전에는 [다음] 버튼이 흐려요. // 왜 못 누르는지 옆에 짧게 알려 주면 더 친절해요.
로딩 | 버튼을 누른 뒤 일이 끝나길 기다리는 동안 빙글빙글 도는 모습이에요. // 이걸 보여 주지 않으면 사람들이 안 눌린 줄 알고 여러 번 눌러요. // 로딩 중에는 다시 누를 수 없게 막아 두는 게 좋아요.
성공 | 일이 잘 끝났다고 체크 표시로 잠깐 바뀐 버튼이에요. // "저장됐어요"를 따로 띄우지 않아도 버튼 자체가 알려 줘요. // 1~2초 뒤 원래 모습으로 돌아오게 해요.
오류 | 일이 실패했다고 빨갛게(또는 경고 표시로) 바뀐 버튼이에요. // 무엇이 잘못됐는지 짧은 글을 함께 보여 주면 다시 시도하기 쉬워요. // 색만으로 알리면 색을 구분하기 어려운 사람이 놓칠 수 있어 아이콘도 함께 써요.
선택됨 | 여러 개 중 골라 놓은 상태로 계속 남아 있는 버튼이에요. // 필터 버튼, 세그먼트처럼 무엇을 골랐는지 계속 보여 줘야 할 때 써요. // 색을 채우거나 체크 표시를 붙여 구분해요.

플로팅 버튼 | 화면 구석에 동그랗게 떠 있는 버튼이에요. FAB라고도 해요. // 스크롤해도 같은 자리에 있어서 "글쓰기 +"처럼 자주 쓰는 행동에 좋아요. // 내용을 가리지 않게 위치를 조심해요.
CTA 버튼 | Call To Action, 즉 "행동하세요" 버튼이에요. // "지금 시작하기", "무료로 써 보기"처럼 사용자가 꼭 눌러 주길 바라는 핵심 버튼이에요. // 크고, 눈에 띄는 색으로, 무엇을 하게 되는지 분명한 말로 써요.
토글 버튼 | 누를 때마다 켜짐과 꺼짐이 번갈아 바뀌는 버튼이에요. // 굵게(B) 버튼, 좋아요 하트처럼 상태가 바뀐 걸 버튼 모양으로 보여 줘요. // 지금 켜진 상태인지 꺼진 상태인지 확실히 구분돼야 해요.
버튼 그룹 | 관련된 버튼 몇 개를 붙여서 한 묶음으로 둔 거예요. // 왼쪽·가운데·오른쪽 정렬 버튼처럼 같은 종류의 일을 하는 버튼들을 모아요. // 묶여 있으면 서로 관련 있다는 게 한눈에 보여요.

## 메뉴 버튼 모양
햄버거 | 가로줄 세 개(☰)로 된 메뉴 버튼이에요. 빵-고기-빵 햄버거를 닮았어요. // 누르면 숨어 있던 메뉴가 옆이나 위에서 나와요. // 휴대폰처럼 좁은 화면에서 메뉴를 숨겨 둘 때 가장 많이 써요.
케밥 | 세로로 점 세 개(⋮)가 놓인 버튼이에요. 꼬치 케밥을 닮았어요. // 누르면 수정, 삭제, 공유 같은 추가 메뉴가 작게 펼쳐져요. // 카드나 목록 항목 오른쪽 위에 자주 붙어요.

홈 인디케이터 | 아이폰처럼 버튼 없는 휴대폰 화면 맨 아래의 가로 막대예요. // 밀어 올리면 홈 화면으로 가요. // 앱을 만들 때 이 막대에 버튼이 가리지 않도록 아래 여백을 둬요.

## 평점 UI
별점 | 별 다섯 개 중 몇 개를 칠하는지로 점수를 매기는 거예요. // 누구나 익숙해서 설명 없이도 바로 쓸 수 있어요. // 학생들의 활동 소감이나 책 추천 점수에 쓰기 좋아요.
반 별점 | 별을 반 개 단위까지 칠해서 4.5점처럼 보여 주는 거예요. // 여러 사람의 평균 점수를 더 정확하게 보여 줄 때 써요. // 직접 고를 때는 반 개가 헷갈릴 수 있어서 보여 주기용으로 많이 써요.
NPS 점수 | "친구에게 추천하고 싶나요?"를 0부터 10점 중에 고르게 하는 평가예요. // 9~10점은 추천하는 사람, 0~6점은 아닌 사람으로 나눠서 얼마나 만족하는지 봐요. // 수업이나 앱의 전체 만족도를 알아볼 때 써요.
이모지 평가 | 웃는 얼굴부터 우는 얼굴까지 표정 중에 골라 기분을 알려 주는 평가예요. // 숫자보다 쉽고 직관적이라 어린 학생도 바로 할 수 있어요. // 오늘의 기분, 활동 난이도 묻기에 좋아요.
좋아요·싫어요 | 엄지 위·아래 두 가지로 간단히 평가하는 거예요. // 고민할 필요 없이 한 번에 누를 수 있어서 응답이 많이 모여요. // 자세한 이유가 궁금하면 누른 뒤 짧은 질문을 이어서 물어요.
평점 슬라이더 | 손잡이를 좌우로 밀어 점수를 고르는 평가예요. // 0~10처럼 촘촘한 점수를 고를 때 좋아요. // 양 끝에 "어려워요 ↔ 쉬워요"처럼 뜻을 적어 두면 알기 쉬워요.
평점 요약 | 평균 점수와 점수별로 몇 명이 골랐는지를 막대로 한눈에 보여 주는 거예요. // "★4.6 · 5점 30명, 4점 8명…"처럼 전체 분위기를 알 수 있어요. // 평가가 많이 모인 뒤에 보여 주는 화면이에요.
평가 태그 | "재미있어요", "쉬워요", "길어요"처럼 이유를 골라 누르는 평가예요. // 점수만으로는 알 수 없는 '왜'를 쉽게 모을 수 있어요. // 글로 쓰기 어려워하는 학생도 쉽게 의견을 낼 수 있어요.
평점 배지 | 카드 구석에 "★ 4.8"처럼 점수를 작게 붙인 표시예요. // 목록에서 여러 개를 비교할 때 점수를 바로 볼 수 있어요. // 평가가 몇 개인지 "(23)"처럼 함께 적으면 믿음이 가요.

## 날짜 고르는 UI
인라인 달력 | 버튼을 누르지 않아도 화면 안에 늘 펼쳐져 있는 달력이에요. // 날짜 고르기가 주된 일인 화면에서 바로 고를 수 있어 편해요. // 자리를 많이 차지해서 다른 내용이 많은 화면에는 팝오버 달력이 나아요.
팝오버 달력 | 날짜 칸을 누르면 그 바로 아래에 작게 튀어나오는 달력이에요. // 평소엔 숨어 있어서 자리를 차지하지 않아요. // 날짜를 고르면 자동으로 닫히고 칸에 날짜가 들어가요.
월 그리드 | 1월부터 12월까지를 바둑판으로 보여 주고 달을 고르는 화면이에요. // 날짜보다 달을 빠르게 고를 때 좋아요. // 달력에서 맨 위 "2026년 3월"을 누르면 이 화면으로 바뀌기도 해요.
휠 피커 | 연·월·일이나 시간을 위아래로 돌려서 고르는 바퀴예요. // 휴대폰 알람 시간 맞추기처럼 엄지로 돌리기 편해요. // 생일처럼 먼 날짜를 고를 때 달력보다 빠를 수 있어요.
직접 입력 | 날짜를 2026-03-02처럼 직접 타자로 치는 방법이에요. // 이미 날짜를 알고 있다면 고르는 것보다 빠를 수 있어요. // 형식을 예시로 보여 주고, 잘못 쓰면 바로 알려 줘야 해요.
캘린더 | 일정을 달력 모양으로 보여 주는 화면이에요. 날짜를 고르는 부품과는 조금 달라요. // 칸마다 그날의 일정이 적혀 있어서 한 달 계획을 한눈에 볼 수 있어요. // 월·주·일 보기를 바꿀 수 있게 만들기도 해요.
월 선택 | 날짜 없이 연도와 달만 고르는 거예요. // "3월 학급 기록 보기"처럼 날짜까지는 필요 없을 때 써요. // 화살표로 이전 달, 다음 달로 넘기는 방식이 많아요.
범위 달력 | 달력에서 시작 날과 끝 날을 차례로 누르면 그 사이가 칠해지는 달력이에요. // 기간이 한눈에 보여서 며칠인지 바로 알 수 있어요. // 체험학습 기간, 방학 기간을 고를 때 써요.
기간 선택 | 시작 날과 끝 날을 골라 기간을 정하는 기능이에요. // 달력으로 고르기도 하고, 날짜 칸 두 개로 따로 고르기도 해요. // 끝 날이 시작 날보다 앞서지 않게 막아 줘야 해요.
체크인·체크아웃 | 숙소에 들어가는 날과 나오는 날을 고르는 달력이에요. // 범위 달력과 비슷하지만 "몇 박"인지가 중요해요. // 수련회 날짜 정하기 같은 활동에도 응용할 수 있어요.
시간 슬롯 | 예약할 수 있는 시간을 버튼으로 늘어놓은 거예요. "10:00, 10:30, 11:00"처럼요. // 이미 찬 시간은 흐리게 해서 고를 수 없게 해요. // 상담 예약, 특별실 예약 앱에 잘 맞아요.
반복 설정 | 일정이 매일, 매주, 매월처럼 되풀이되는 규칙을 고르는 기능이에요. // "매주 화요일 3교시 방과후"처럼 한 번만 정하면 계속 들어가요. // 언제까지 반복할지 끝나는 날도 함께 정해요.
빠른 선택 | "오늘, 내일, 다음 주 월요일"처럼 자주 쓰는 날짜를 한 번에 고르는 기능이에요. // 달력을 열지 않아도 돼서 빠르고 편해요. // 과제 마감일 정하기처럼 가까운 날짜를 자주 고를 때 좋아요.
빠른 선택 칩 | 빠른 선택을 작은 알약 버튼으로 늘어놓은 거예요. // 날짜 칸 바로 아래에 "오늘 · 내일 · 이번 주"처럼 놓여요. // 누르면 날짜 칸이 바로 채워져요.

자동완성 | 글자를 치는 동안 아래에 추천 낱말이 뜨는 기능이에요. // 끝까지 다 치지 않아도 고를 수 있고, 맞춤법이 헷갈려도 찾아 줘요. // 키보드 화살표로도 고를 수 있게 만들면 좋아요.
최근 검색어 | 내가 전에 찾았던 낱말을 다시 보여 주는 기능이에요. // 같은 것을 또 찾을 때 다시 칠 필요가 없어요. // 하나씩 지우거나 모두 지우는 버튼도 함께 둬요.
인기 검색어 | 다른 사람들이 많이 찾는 낱말을 순위로 보여 주는 기능이에요. // 무엇을 찾을지 모를 때 힌트가 돼요. // 학급 앱이라면 "많이 본 자료"처럼 응용할 수 있어요.
필터 | 조건을 골라 결과를 걸러 보는 기능이에요. 체로 거르듯이요. // "3학년 · 국어 · 활동지"처럼 조건을 고르면 맞는 것만 남아요. // 지금 어떤 필터가 켜져 있는지 칩으로 보여 주면 헷갈리지 않아요.
정렬 | 결과를 최신순, 이름순, 인기순처럼 순서대로 줄 세우는 기능이에요. // 필터는 '무엇을' 보여 줄지, 정렬은 '어떤 순서로' 보여 줄지를 정해요. // 지금 무슨 순서인지 버튼에 표시해 둬요.
검색어 강조 | 검색 결과 속에서 내가 친 낱말을 색칠해 보여 주는 거예요. // 왜 이 결과가 나왔는지 한눈에 알 수 있어요. // 이 사전의 검색도 찾은 글자를 파랗게 강조해요.
